## 목표
AI 평가 결과를 누가, 언제, 무엇을 보고 검토하고 확정하는지 정하고, 형식적 검토에 그치지 않게 하는 장치를 설계한다.

## 배경
- 강사에게 불이익이 생기는 판정은 사람 검토 없이 확정하지 않는다. (`AGENTS.md:27`)
- 확신도가 낮은 판정은 사람 검토 큐로, 검증되지 않은 항목은 `verified=false`로 참고용으로만 노출한다. (`docs/02-specs.md:39`, `:40`)
- 강사는 결과와 근거를 열람하고 재평가를 요청할 수 있고, 등급 보류·투입 제한은 반드시 사람이 검토한다. (원본 기획서 8장)
- 스키마에는 `review_status`(상태)만 계획돼 있고, 누가·무엇을 검토하는지는 정해진 것이 없다.
- 벤치마킹(261001, 웹 검색 요약 수준이라 원문 확인 필요): AI 면접 업체는 "AI는 점수와 근거를 주고 사람이 결정"하는 구조를 내세운다. 상위 후보만 사람이 검토하면 하위 결과가 걸러지지 않고, 검토가 형식적이 되는 자동화 편향이 문제로 지적된다. 사람이 같은 루브릭으로 평가하는 거부(opt-out) 경로도 있다.

## 완료 조건
(항목 중 "제안"은 벤치마킹에서 나온 아이디어이며 확정이 아니다)
- [ ] 검토 대상 선정 기준: 불이익 가능 판정 전부, 낮은 확신도, 판단 불가, 미검증 항목. 하위(불리한) 결과도 포함. 나머지는 무작위 표본 감사 (제안)
- [ ] 검토 주체와 권한: 누가 검토하나(커리큘럼팀 / 전문가 / 선배 강사), 자격, 이해충돌(자기 평가 금지 등)
- [ ] 검토 흐름과 기한: 큐 → 검토 → 확정/수정 → 강사 통보. 처리 기한
- [ ] 검토 화면 요구사항: 판정, 루브릭 항목 정의, 근거(타임스탬프로 해당 음성 구간 바로 재생), AI 확신도
- [ ] 검토 결과 기록 항목: 검토자, 시각, 원 결과, 수정 결과, 사유. 스키마 `review_status` 확장 필요 여부 결정
- [ ] 강사의 열람·재평가 요청 절차: 재평가는 기존 검토자와 다른 사람이 하는지, 같은 루브릭으로 사람이 평가하는 경로
- [ ] 형식적 검토 점검 방법: 검토자의 수정 비율 기록, 일부는 AI 결과를 가리고 평가해 일치도 확인 (제안)
- [ ] 수정 데이터 활용: 검토에서 뒤집힌 사례를 루브릭·eval 개선에 쓰는 방법과 정책상 허용 범위
- [ ] 결정 내용을 `reports/`에 기록하고 schema-v0·policy-confirmation에 반영
